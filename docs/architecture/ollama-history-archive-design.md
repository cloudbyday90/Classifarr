# Gateway history archive and retention assessment

Design, 2026-10-15. Offline, opt-in and local synthetic validation only.

## Decision and scope

History is bounded at 100,000 bindings. Removing append-only rows or decrementing
the counter without recoverable evidence would lose ownership/recovery history.
The first retention implementation therefore provides `inspect`, `create` and
`verify`: a report, a complete native gateway-schema archive and an integrity
check. It does **not** purge, reset capacity, replay requests or enable unattended
operation. Fresh/unconfigured installations do nothing automatically.

Use a dedicated connected session and the existing gateway advisory lock. Refuse
running gateways and reentrant/shared sessions. Read schema v7 and the explicitly
configured provider only. An uninitialized provider or wrong schema is not an
empty success. Archive active/uncertain work unchanged; acquiring a database lock
is not proof that provider compute stopped.

A read-only repeatable-read transaction produces the report and exports its
snapshot to PostgreSQL 18 `pg_dump`. The schema archive includes all gateway
tables, functions, constraints and indexes, including unknown/legacy bindings,
completion receipts, recovery/stop evidence and TLS peer observations. It omits
ACLs; custom archives can retain ownership metadata, so restore explicitly with
`--no-owner --no-acl` and review grants separately. No schema or tables
are added. The archive identity is generated by PostgreSQL `uuidv7()`.

## Retention report

Require an explicit 1–3,650-day retention horizon; it is advisory, not consent to
delete. Report mutually exclusive counts: active binding, lifecycle evidence,
unknown outcome, recent terminal outcome, older terminal outcome for review.
Only `response_completed`, `provider_rejected` and `not_dispatched` are terminal
review candidates. Both admission and completion must predate the cutoff. A
recovery or provider-stop reference always keeps the binding protected. Missing
legacy bindings and counter mismatches are visible, never corrected. All rows,
including review candidates, are archived and retained in the source database.

## Files, bounds and cancellation

Initial CLI support is Linux with a local PostgreSQL Unix socket. Use an explicit
SELECT-only archive role, private configuration and private local output parent.
Reject symlink paths, unsafe permissions, remote connection strings and overwrite.
Create a new private archive directory; files are mode 0600. A manifest is the
completion marker, written exclusively and synced only after dump success and the
read-only transaction commits. A failed command can leave partial output or an
unsynced marker; mere marker presence does not establish successful durability.
Do not automatically delete administrator-owned archives.

Fixed executable, no shell, no ambient libpq credentials/settings, no password
arguments and no raw child errors. Stream the dump with backpressure, maximum
256 MiB, 60-second dump timeout, bounded SQL/lock timeouts and a 120-second CLI
deadline. Cancellation kills the child and rolls back the read transaction.
No automatic retries. A new explicit invocation uses a new archive UUIDv7.

Verification checks bounded private regular files, manifest shape, size and
SHA-256 without invoking PostgreSQL or restoring SQL. It proves byte integrity
against that manifest, **not** authenticity, successful restore or permission to
purge. Store the returned manifest hash separately in trusted storage. Archives
contain private operational references; never upload them to issues or Git.

## Research and tradeoffs

Official sources discovered/opened through MCP on 2026-10-15:

- [PostgreSQL transaction modes](https://www.postgresql.org/docs/18/sql-set-transaction.html)
  support a stable repeatable-read snapshot and read-only restrictions.
- [pg_dump](https://www.postgresql.org/docs/18/app-pgdump.html) supports custom
  archives and an exported snapshot. Schema-only selection can omit external
  dependencies; verify the isolated gateway schema by actually restoring it.
- [pg_restore](https://www.postgresql.org/docs/18/app-pgrestore.html) warns that
  restoring executes source-controlled SQL. Never make integrity verification
  restore untrusted input or point a rehearsal at live data.
- [Node 24 filesystem APIs](https://nodejs.org/download/release/v24.20.0/docs/api/fs.html)
  provide exclusive creation and explicit file synchronization. Use private local
  filesystems; this is not a durability promise for arbitrary network storage.

| Option | Pros | Cons |
| --- | --- | --- |
| Age-based deletion now | Reclaims capacity | Can erase uncertain/linked evidence; no verified archive prerequisite |
| Custom row export | Selective and readable | Requires a new restore format and dependency ordering |
| Native archive plus assessment (selected) | Preserves schema and evidence; testable restore | Requires offline window and storage; does not reclaim capacity yet |

Recommended stack: small ESM contract/report/archive/file/CLI modules, PostgreSQL
18 UUIDv7 and custom dumps, SHA-256 manifest, least-privilege socket connection.
Keep normal gateway and application defaults unchanged. Tests must cover busy
owners, bad provider/schema, protected/legacy/recent rows, read-only access,
cancellation, corrupt/incomplete/oversized files and actual isolated restore.

Next: reviewed purge policy and archive retrieval with retained tombstones and
explicit authorization. Never weaken immutable evidence or admission limits as
a shortcut. Real-provider rollout remains separately approved.
