receipt records, guarded actions, query generation and the CLI/public projector.
They are private preparation material, not an installed product admin feature.
No HTTP API, database, dependency, background service or general resume mode was

The new inspect query physically omits all receipt/resource writers and root
pinning. It reuses the reviewed parent/root/metadata boundaries, then checks
the selected VM's state, settings, paths, adapter, checkpoints and disk, plus
other-VM disk references and every expected file's basename, owner, attributes,
native identity and ACL fingerprint. Two complete snapshots must agree before
it proposes a current target fingerprint. Filesystem enumeration order does not
change that fingerprint. Resource counts, fixed steps/errors and numeric codes
are public; raw identities and provider errors are not.

Inspection has one restricted 30-second/64 KiB call and no retry. Its frozen
source hash is e3702fadcc59fa84e03be9a092ae957a01918793460cd38678a1bad9cd5c8f2b.
The separate prepared apply query is tested only with all VM/VHD and fixture
resource effects mocked. It is not reachable from the packaged CLI. A future
enablement would require explicit current-identity review, a separately pinned
apply source and bounded execution wrapper, and separate execution agreement.
No such enablement or agreement is claimed here.

## Receipt and partial outcomes

The prepared sequence exclusively creates a protected one-shot receipt inside
the private fixture root only after fresh admission and approved-fingerprint
comparison. It never opens/truncates an existing claim. The initial flushed
record preserves the full current private identity snapshot, including VM GUID,
disk identifiers and exact tree. This is current-target evidence, not recovered
evidence from the original creator.

Every VM/file/directory call needs a flushed intent identifying its exact
subject fingerprint, then a fresh safety check. Verified absence receives a
subsequent record. Per-leaf fingerprints map directly to the persisted claim
tree; ordinal alone would be ambiguous when native VM removal leaves a
different subset. A stop record retains safe failure details if writing it
succeeds. A failed/partial flush stops subsequent effects, keeps the claim and
reports uncertainty. No finally-block removal or automatic retry is present.

After VM removal, require exact VM absence and safe disk references before
accepting only unchanged inspected survivors. Later operations require exact
remaining inventory, then remove individual expected files and empty folders.
The root and receipt remain. Unexpected permission/native-identity/attribute
changes stop the sequence; no ownership or permission baseline is refreshed.
Before each check/effect, old absence/count results are invalidated rather than
reported as current facts after a failure.
