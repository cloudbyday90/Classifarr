# Adopted RAG recheck advice provenance design

Research: November 11, 2026 Eastern. Baseline main
`e9c6d87d696f83c381944f9667b5e478741a9a0a`. The operator confirmed the
consumer boundary in Q1 and the complete contract in Q2 before runtime
implementation. The separate
[investigation](rag-recheck-advice-provenance-investigation.md) contains source
traces, official guidance, alternatives and current PR assessment.

## Confirmed first consumer

Qualify optional advice/profile only for the existing RAG branch that already
has an adopted candidate and a prompt-confirm policy outcome. Preserve the
existing verification context/helper, target, admission, instructions, parsing,
adoption, AI counters/caps, resilience, retries, rollout and routing/learning
authority. Missing evidence omits optional material rather than refusing or
authorizing verification.

Keep non-adopted verification, generic/legacy callers, adjudication and its
purpose disclosure, and private replay unchanged. Leave final result/persisted
`signalContext` precedence unchanged. Those separate contracts can still retain
earlier context and are not repaired by this optional-provider-evidence batch.

## Fresh source and successful-stage handoff

Use a small RAG-specific leaf and the established verification projection/profile
session. Do not rewrite the shared scoring-context builder or the compatibility
verification helper.

1. Immediately after the existing awaited reevaluation succeeds, before adoption
   callbacks, hold a private source against that exact result, expanded metadata
   object and original loaded library pool. Construct a minimal source context
   from the actual retained ranked reference, overall confidence and selected
   pool object; never spread the earlier context into this source.
2. Require the existing genuine live selection witness. Preserve strict typed
   item identity, enabled native/compatibility origin, native revision where
   applicable, exact result/ranking/decision and loaded-pool checks. No receipt
   can be minted from matching IDs, diagnostics, hashes or historical data.
3. Tie the source to the exact successfully returned policy-stage object and its
   actually adopted prompt-confirm candidate through private runtime state.
   Check the result/candidate association when handing it onward. Do not add
   public stage/result fields, persisted metadata, trace/log payloads or a new
   database capture. Skips, failures, timeouts and late results do not create a
   successful-stage handoff; a retained earlier result is not a substitute.
4. Consume the stage handoff once through the existing service orchestration.
   Copies/serialization, another stage, item, result, pool or candidate cannot
   reuse it. Missing/invalid handoff leaves an explicit internal scoped request
   with unavailable optional evidence, not fallback to raw earlier context.
5. In the adopted rerun branch, keep the existing retargeted verification
   context exactly as produced today. Bind the fresh advisory source to that
   exact consumer context with a private guard requiring the same selected pool
   object and the same numeric overall confidence. Do not coerce values or
   replace authority inputs to make optional evidence fit.

Private evidence failure cannot throw into the evaluation retry path, create
another evaluation or change stage success/adoption. The new handoff records
what the existing successful path proves; it is not new provider permission.
Non-adopted requests do not enter this scoped consumer. Failed/skipped rechecks
normally produce no adopted candidate and retain their excluded behavior.

## Reused projection and asynchronous checks

Reuse the established selection-only advice: held display label and original
overall confidence. Do not send the earlier breakdown, diagnostics or related
text, nor claim the fresh private reference proves those fields. Do not let an
explicit policy-section override bypass the scoped projection.

Keep the current bounds: 64 evaluated candidates, 64 libraries and a 16-KiB
selection witness; 160-UTF-16-unit labels; 16 KiB of combined encoded optional
advice/profile data. Keep fixed own-data-property inspection, proxy/accessor
refusal, immutable projections, whole-section overflow omission and the existing
5-rating/5-genre/3-studio display prefixes plus fixed coverage traits.

The existing profile lookup runs only after provider admission and valid source
and consumer checks. Its exact requested library/result association remains
private. Recheck source and consumer after awaited work, including the profile
read, prompt assembly and provider-lock wait, and at each existing generation
attempt. Observed invalidation remains permanent for that session; restoring
fields cannot refill its gap.

Use an additional validity guard within the existing session lifecycle so source
or consumer invalidation uses the same bounded omission rebuild. Retain at most
a qualified build plus one omission build per existing generation attempt.
Initial verification still requires its exact original source context; the RAG
guard adds a separate condition and cannot weaken that initial-call contract.

Preserve the existing transport attempt limits and assembly-error separation:
assembly failures propagate and release the lock without becoming provider
retries, refusal observations or capability invalidations. Optional omission
does not add, refund, replay or reclassify a provider call.

Profile data remains a later inventory observation with existing coverage and
untrusted-data wording, not a verified label or declared purpose. Preserve
current provider disclosure for those existing fields; add no purpose terms,
titles, raw rules, private references, revisions or internal IDs to transport,
history, logs or caches.

## Meaning and resource limitations

The evidence proves loaded-snapshot association at the application generation
boundary. It does not prove current database configuration, full metadata/rule
immutability, profile accuracy, a uniquely correct destination or classification
correctness. No new freshness query, provider call or configuration read is
introduced.

The existing inventory query, native Promise/thenable assimilation, provider
lock and transport retain their existing behavior. Projection limits do not
bound database rows/query duration or whole-worker shutdown. Existing late
evaluation behavior is not replaced with a cancellation/replay protocol.

## Recommendations and tradeoffs

The private handoff and additional guard reuse the existing evaluator and
projection, avoid new durable state and preserve verification authority. The
cost is less optional explanatory text and another small runtime association
to verify. Keeping one omission lifecycle prevents nested rebuild/retry rules.

Recommendation stack:

1. Deliver adopted-candidate optional advice/profile with a fresh private source
   and unchanged verification authority.
2. Assess non-adopted verification separately: replacing its old context can
   change admission, parsed confidence and provider dispatch.
3. Assess retained/persisted result context separately, including its baseline
   precedence and historical evidence semantics.
4. Consider broader signal/diagnostic provenance or database freshness only
   through explicit contracts, without treating provenance as accuracy or
   additional action permission.
