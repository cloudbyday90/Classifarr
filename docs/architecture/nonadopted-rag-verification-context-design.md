# Fresh non-adopted RAG verification context design

Research: November 11, 2026 Eastern. Baseline main
`37cd4c38edf2c360bdf81cab3e7532434dd3beaf`. Q1 and Q2 confirm coherent fresh
non-adopted verification or baseline retention and the complete application-
boundary lifecycle below. The user accepted the complete batch before implementation.
The separate [investigation](nonadopted-rag-verification-context-investigation.md)
records source traces, a pure-function reproduction, official guidance and PR
assessment.

## Confirmed behavior

Use the fresh selected destination and original overall confidence together for
non-adopted RAG reruns that already pass the existing eligibility and explicit
verification-mode gates. Require genuine successful fresh prompt-confirm stage
evidence. Missing, retained, copied, malformed or over-budget evidence skips the
rerun and preserves the baseline without generation or a guessed fallback.

This is an intentional behavior change: a former candidate mismatch can become
valid provider admission, and fresh confidence/destination can change successful,
ABSTAIN, invalid-output or provider-refused review results. Existing comparison
and apply/shadow rollout still decide final adoption. Do not flip the
intermediate policy gate or claim freshness proves correct classification.

Keep material-improvement/action-upgrade skips, configured caps, capability/schema
requirements, score/ranking formulas and routing/learning authorization intact.
Do not broaden `shouldVerifyPolicyRecheckCandidate` or its existing eligibility
exception. Adopted/initial verification, generic/legacy paths, adjudication,
private replay and retained/persisted-context precedence remain separate.

## Private fresh-stage evidence

Use a dedicated modular leaf for this authority-sensitive consumer, reusing the
existing genuine numeric live-selection witness rather than diagnostic or
optional-profile availability. Capture immediately after the existing awaited
reevaluation succeeds, before later adoption callbacks.

Bind the exact expanded item/result objects, typed identity, policy/library pairs,
native revision where applicable, retained decision/ranking/overall confidence
and original loaded library pool. Carry a private association with the exact
successful non-adopted stage and gate: no error, no adopted candidate, and the
unchanged fresh prompt-confirm result. Do not weaken the adopted-only handoff or
fabricate a candidate merely to reuse it.

Consume a successful-stage handoff once into a closed fresh verification context
and private request lifecycle. Copying/serialization, another stage/item/result/
pool, altered source evidence or a late evaluation cannot recover that authority.
Do not infer fresh success from `policyAfter`, public flags, fields or hashes.

The new context contains fresh destination/confidence and the exact retained
ranked reference needed by private readers. Do not spread earlier breakdown,
diagnostics, related text or defaults into it, substitute the leading score,
take maximum baseline confidence, or change earlier context in place.

Preserve the existing 64-candidate/64-library and 16-KiB closed selection-witness
bounds. These limits now affect this consumer's availability: unavailable proof
means baseline retention. They are not permission to reconstruct or truncate
missing evidence.

Keep optional advice/profile independent. Reuse its bounded selection-only
projection, 160-unit labels, 16-KiB combined data cap, fixed coverage and existing
display prefixes. Missing/invalid optional material omits those sections while
a valid numeric verification reference may still proceed. Do not turn a profile
or full-label formatting gap into implicit routing or verification authority.

## Continued validity at application boundaries

Check the private reference before AI-service invocation. Recheck on fulfilled
configuration/provider/admission continuations, outside optional-profile catches,
inside provider-lock cleanup coverage, after prompt assembly and at each existing
application generation-attempt entry. Observed invalidation remains a gap for
that lifecycle; do not refill it by restoring fields later.

Also recheck after the awaited AI-service result, before constructing or adopting
a rerun candidate. This covers early provider-admission returns and proof loss
during entered transport, parsing, cost/usage writes or capability observation.
Keep existing actual provider observations; do not erase or duplicate them.

The generation-entry check is not an exact socket/HTTP-dispatch fence. Ollama
and gateways can await configuration/preflight after entry, and cloud transport
can perform usage writes. Do not add transport hooks, new cancellation, deadlines
or immediate termination promises. Work already entered can complete; invalid
proof prevents accepting its result, not an assertion that no request occurred.

## Local refusal, genuine errors and accounting

Use a private trusted refusal identity, not a provider-supplied error code,
message or public field. Recognize that local refusal before RAG failure
classification/resilience handling. Return the existing skipped/no-candidate
stage shape and let the outer flow retain baseline. Use a fixed existing context-
unavailable reason; never call the null-context legacy default-library path.

| Point of refusal | Invocation count | Work/outcome |
| --- | --- | --- |
| Missing proof before AI-service call | Unchanged | Skip without new provider/config/profile work |
| Proof lost after AI-service entry, before generation | Existing invocation stays charged | No new generation; local refusal is not provider failure |
| Valid proof, provider not admitted | Existing invocation stays charged | Existing fresh-context refusal result; no generation |
| Proof lost after transport entry | Existing invocation stays charged | Preserve actual observations, discard rerun result, retain baseline |
| Real attempt failed before proof prevents retry | Existing invocation stays charged | Preserve that real error and observations; no additional application attempt |

Preserve genuinely rejected database/provider/admission/transport operations;
do not replace them from catch-time freshness checks. If an actual stream error
already exists when proof prevents a retry, preserve that error's classification
and observation rather than suppressing it as a local refusal.

A pure proof refusal cannot trigger provider cooldown, capability invalidation,
repair, retry, a new provider attempt, refund or replay. Preserve all existing
cleanup and metric-failure precedence. This does not make final evidence checks
atomic with existing cost/usage/capability writes or undo completed observations.

## Disclosure, storage and resource boundaries

Add no database query, provider setting, schema/capture version, public result
field, persistent proof, scheduled job, UI or operator CLI trigger. Keep private
references out of logs, history, API responses, caches and portable evidence.
Do not add purpose terms, raw rules, retrieved titles or new provider disclosure.
Existing profile placement remains observed evidence, not verified labels.

This proves loaded-snapshot consistency at named application boundaries. It is
not current database freshness, full metadata/rule immutability, accuracy or
whole-worker shutdown. Existing query duration, Promise assimilation, provider
lock and transport behavior retain their own limits and authorization.

Verify actual fresh native/compatibility evaluation and stage provenance with

retry and entered-transport/metrics work; private refusal versus forged error
codes; counter boundaries and real-error precedence. Preserve existing initial/
adopted, caps/material-improvement/action-upgrade, routing and learning controls.

Keep paid/authenticated providers and live data outside tests. Run focused checks,
fresh backend coverage and normal affected gates. Reuse client coverage only with
unchanged relevant inputs, installed graph and report hashes. Apply scoped
artifact maintenance before heavy verification and at handoff.

Retain PR 589's demonstrated compiler deferral while its artifact remains
unchanged; rebase only genuinely stale applicable branches. Record actual results
in a separate outcome, update Unreleased, inspect all intended changes, then
commit/push on main and inspect that revision's CI. No branch, live configuration
write, release or deployment is created.

## Recommendations and tradeoffs

The benefit is a coherent verification request and explicit baseline retention
for unknown evidence. The costs are changed dispatch/review results, conservative
availability limits and a small private local-refusal lifecycle. Reusing existing
selection/profile readers and current stage/result shapes avoids another durable
system or operator workflow.

Recommendation stack:

1. Deliver fresh non-adopted verification with application-boundary validity,
   truthful invocation counts and no guessed fallback.
2. Assess retained/persisted result context separately; its baseline precedence
   remains unchanged and must not be described as repaired.
3. Consider transport-internal fencing or stronger database freshness only with
   explicit cancellation, availability and uncertain-outcome contracts.
