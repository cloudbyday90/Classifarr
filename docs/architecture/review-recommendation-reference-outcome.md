## Implemented behavior

A small pure server leaf resolves the retained policy candidate once. The answer
builder passes that same reference to the recommendation and deterministic
summary. Recommendation v2 keeps technical policy evidence, bounded advisory
proposal and optional primary offer separate. Scores are finite candidate-bound
numbers; null/empty/global confidence cannot become a named score. Incoherent,
duplicate, overflowing or tied candidate evidence cannot establish a primary.
A coherent explicit retained top may identify technical evidence during a tie,
but cannot break it. Conservative historical safety refusal remains independent
of the display reference. A separate blocking-only legacy adapter preserves
existing high-score historical holds, including a global-policy score that
previously took precedence over a lower candidate score. It supplies no display
reference or number. A direct comparison against unchanged main reproduced and
verified this safeguard: the old display used 90; the corrected display uses 75;
both require a historical-safety retry. Known policy gates and manual history
confidence alone do not invent this hold. A separate synthetic comparison across
8,640 method/action/score/order combinations retained all 888 old historical
holds, with zero lost holds. It also found 668 additional conservative holds
after reference correction; these require retry, never authorize a route. These
synthetic counts are not production prevalence or classification accuracy.

A current structured proposal must validate and belong to the server shortlist;
names come from server candidates. Disagreement and malformed/unbound current
proposals require explicit destination selection. Absent, unknown or legacy
advice supplies no agreement proof. Existing abstained/rejected diagnostics stay
explanatory. Legacy text and an ai_verified method alone cannot manufacture AI
alignment. Nothing reconstructs older proof from current policies.

Stale reviews explicitly ask for refresh rather than confirmation.
The outer header, score label, inner summary, existing evidence disclosure and
bulk confirmation now follow that meaning. Evidence stays available when a
primary offer is withheld. Long destination names wrap within the existing card
and buttons at narrow widths. There is no extra page, wizard, alert stream or
routine CLI action. Client v1 read compatibility remains; unknown/inconsistent
current projections cannot fall back to mutable destination labels or manual
confidence.

Discord uses the already-supplied persisted metadata, method, confidence, reason
and typed item identity. Its buttons use the same fingerprint as locked-row
validation. Styling follows the identified primary destination rather than array
position; disagreement has no green positional default. Native questions retain
their single destination, original question and null recommendation semantics.

Command version and action meaning remain unchanged. Explicit confirmation can
select any server candidate; a destination change uses the separate existing
active-library action. Changed pending fingerprints receive the existing stale
409 response. Exact completed receipts, including pre-v2 answers, replay before
presentation rebuilding and cannot route again. No schema, endpoint, capture,
job, provider request, historical backfill or learning authority was added.

## Remaining cause and recommendation stack

The shared-reference repair prevents a reproduced misleading review default.
It does not correct the policy ranking. The retained arithmetic demonstrates
that profile-derived genre rules can earn strong native intent weight while
that same library profile separately contributes support and agreement. Native
storage/provenance validation is working; source-aware live weighting is still
incomplete. Weak-evidence calibration kept the sampled candidates below automatic
routing, but did not repair ordering. Removing only the agreement bonus would
leave the observed wrong leaders unchanged. The inspected records contain
confirmed exact-item memories but no generalized policy feedback for these
choices; resolving an item did not rewrite the broad inferred purpose.

1. Deliver the shared review reference and explicit conflict selection, with
   current authority and replay safeguards preserved.
2. Next, plan provenance-aware scoring: distinguish validated matched declared
   purpose from inferred compatibility, account for correlated evidence, and
   verify specialized and generic-library controls before selecting new weights.
3. Use the existing application purpose-review workflow to establish precise
   destination meaning. Inventory proposals remain context until their meaning
   is appropriately established.
4. Investigate old pending-History reconciliation separately through existing
   automatic ownership/recovery boundaries.

The [design alternatives](review-recommendation-reference-design.md#alternatives-and-recommendation-stack)
record benefits and costs. Automatically preferring AI would promote advisory
meaning without adequate independent proof. Lowering thresholds would give the
observed weak wrong leaders more authority. Another dashboard or collection job
would duplicate working automation without fixing scoring.

The recorded npm bundle remediation requirement and November 9 OSV triage expiry
remain separate dependency/security follow-ups before another release. No
exception was renewed or scanner policy changed here. The full workspace npm
audits remain root/client zero and server five low affected nodes in the previously
documented CNA-rejected advisory chain, zero moderate/high/critical; this is not
a claim that every scanner database has removed that finding.
