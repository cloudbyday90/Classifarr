# Adopted select result-context design

November 14, 2026 (America/New_York). Agreed complete batch at main

See the separate [investigation and research](adopted-select-result-context-investigation.md).

## Construction owner

Extend the existing construction-owned result context to new, genuinely adopted
`prompt_select` candidates. Reuse `adoptedRagResultContext.mjs` and the current
stage capture/application calls. Do not duplicate its proof into another leaf or
tie it to saved-frame, optional-advice or invocation permission.

The owned builder defaults the new select candidate's `signalContext` and
`ai_advisory` to null, preserving exact candidate identity and leaving baseline
untouched. Valid independent same-evaluation proof supplies only the frozen outer
context `{ ranked, confidence, suggestedLibrary }`: exact current ranking, fresh
overall policy confidence and the exact loaded leading library. Outcome maximum
confidence remains separate and unchanged. No new AI outcome is created, so the
earlier advisory remains absent.

Keep prompt-confirm's current construction behavior and fulfilled verification
assembly unchanged. Automatic/manual actions, failed/skipped reevaluation and
initial/non-adopted/generic/legacy paths remain outside this extension.

## Proof and refusal

Admit only the two pending policy actions, capture the primitive source action,
and require that same action when consuming the private source once at actual
candidate establishment. Preserve exact policy result, typed item, library pool,
successful stage/gate, selected candidate, method, library and finite retained
confidence checks. Retain native/compatibility origin, native revision and active
media-compatible leading-library validation from the existing numeric witness.

Missing, copied, offline, changed or overflowing proof leaves explicit null; equal
public fields, current configuration or the saved review frame cannot replace it.
The builder clears the inherited fields even when later inspection cannot finish.
Use own-data inspection without coercion, labels, provider text or hostile hooks.
Diagnostic refusal cannot change adoption or replace a genuine operation error.

Keep 64 evaluated candidates / 64 libraries / 16 KiB of closed numeric proof,
without truncation. These bounds do not cap every attribute reachable through
the referenced ranking rows. Retain exact ranking/library references; do not
clone or reinterpret scores, diagnostics or rule semantics.

## Explicit lifetime

Apply once when the actual new candidate is established. The frozen outer object
does not make ranking rows or loaded libraries immutable. Add no terminal-return,
rollout-wait or writer-time refresh/nulling. Later reference mutation may leave
the construction-owned context populated while independent v2 review validation
records an evidence gap.

Do not consume, reassociate or upgrade review/invocation/advice receipts. Existing
saved-frame publication, copy transfer, writer checks, row binding and forced-gap
precedence retain their current contracts. No loaded-snapshot check claims fresh
database configuration or continuing provider permission.

## Processing and presentation

Preserve destination, method, maximum outcome confidence, reason, prospective
verification-status clearing, explicit top-level signals/RAG, their existing
fallback choices and restrictive authority. Select's existing no-verification
short circuit, provider accounting and observations, retries, cancellation,
budgets, cooldowns, error precedence, scoring and threshold bands remain intact.

Final comparison, conflict checks and apply/shadow rollout still choose the
retained result. Current v2 review evidence remains separate: technical policy
leader/score, mandatory destination selection, no primary Confirm/bulk shortcut
and the generic explicit candidate command are unchanged.

The full context is not serialized. Removing earlier nested support can remove
its existing persistence fallbacks and question-builder related-evidence summary.
Explicit top-level sources preserve their normal precedence. Clearing inherited
advisory intentionally changes new decision summaries, answer fingerprints and
Discord IDs. Recover exact completed receipts before current validation; preserve
historical rows and original automated-decision evidence.

No new operator procedure or UI element is needed. This runs within existing
classification, with existing visible destination controls and server validation.

## Trade-offs and recommendation stack

Fresh minimal context preserves genuine current policy support; explicit null and
advisory absence prevent unrelated inheritance. Costs are changed fingerprints,
possible removal of nested fallback data and a construction-only guarantee.
Continuing validation needs a distinct copy/return/writer contract and is deferred.

Recommended stack: existing live numeric witness, exact action-bound construction
owner, fresh minimal context or null, no inherited advisory, independent current
review validation, existing final apply and transactional persistence, then exact
completed-answer recovery. Keep policy evidence, AI output and authorization
separate.
