# Retained adopted result context design

November 14, 2026 (America/New_York). Agreed implementation of the two confirmed
behavior boundaries; final shared-scope agreement was received. Base: main
`fdde1000f1072ad693e7b319bb082ed5e972bd12`. See the separate
[investigation and official research](retained-adopted-result-context-investigation.md).

## First consumer

Cover the new deterministic prompt-confirm candidate created by a genuine
successful adopted policy reevaluation. Establish its result-owned
`signalContext` and `ai_advisory` at construction, before later verification
gates. Ordinary retained skips, genuine transient/permanent failures and
freshness refusals then carry that same candidate without earlier support.

Use a genuine fresh minimal context containing the exact current ranking,
fresh overall policy confidence and exact loaded selected library. When the
same-evaluation proof is unavailable, use explicit null. Clear inherited
`ai_advisory` at the same boundary: an earlier advisory is not an output for
the new candidate. Fulfilled current verification continues to supply its
actual invocation context and current advisory or explicit absence afterward.

Preserve destination, maximum outcome confidence, method, reason, current
top-level policy/RAG data, restrictive authority and prospective verification
status clearing. Do not remove a generic `result.context` field: no relevant
classification consumer of such a field was demonstrated.

## Private proof and modular implementation

Use a small purpose-specific ESM leaf, separate from the broad orchestration
service. Reuse the existing live numeric witness and reader, with a private
single-use source captured immediately after successful reevaluation and before
adoption callbacks. This consumer must not depend on saved-frame detail capture,
optional prompt advice/profile or AI invocation authority.

At actual candidate establishment, require exact policy result, typed item,
loaded library pool, successful stage/gate and candidate association. The
selected library must be the genuine active media-compatible evaluated leader;
native/compatibility provenance and native revision retain existing checks.
Do not reconstruct proof from equal public objects, old metadata or a saved
frame. Missing, copied, offline, changed or overflowing sources give null.

Keep the existing 64-candidate / 64-library / 16-KiB numeric-witness limits. These
bound the closed proof, not the complete size of every referenced ranking row.
Keep the exact loaded ranking/library references under a frozen outer minimal
context; do not clone or reinterpret their semantics. Read only the existing
fixed own-data proof fields without coercion, labels or provider text.

Preserve the actual new candidate identity. Candidate defaults must already clear
the two inherited fields for this action if proof inspection cannot complete.
Diagnostic failure cannot change adoption or replace an ordinary operation error.
Do not mutate the original baseline. No extra database/provider call is needed.

## Explicit lifetime

This is construction-time ownership, not a promise of continuing freshness.
Ranking rows and the loaded library remain mutable references. Later mutation,
preparation/provider/error-handler awaits, terminal returns, rollout awaits and
writer waits do not refresh or null this context in this batch.

The saved review frame remains a separate consumer with its existing checks at
publication, copy transfer, writer entry, state derivation and pre-INSERT. A
later gap must stay a gap even when construction-owned numeric context remains
populated. Context cleanup must never reassociate or upgrade a forced gap.
Likewise, valid label-free numeric context can coexist with an invocation
refusal caused by its separate display-prefix contract.

Do not consume another consumer's stage/observer/invocation token, alter provider
permission or add a late persistence-lifetime contract. Terminal-return and
writer-time context validation remain separate possible extensions.

## Persistence and presentation

The full signal context is not serialized. Removing earlier nested signals/RAG
can remove their existing persistence fallbacks. Explicit top-level
`result.signals` and `result.ragContext`, including their current existing
fallback choices, retain their normal precedence and values. Preserve all
other top-level result fields and original automated metadata.

Clearing the retained policy candidate's advisory removes its generic legacy
advisory notice. Decision summaries, answer fingerprints and Discord custom IDs
can therefore change for new affected records. Current-frame recommendation,
score and evidence retain their separate source. New question construction
has no earlier related-evidence summary; normalized questions keep their
existing current policy/candidate semantics.

Existing completed-answer receipt recovery still precedes new validation.
Historical rows are not rewritten. Existing restrictive `ai_authority` is
preserved, as are provider observations, charged invocations, CBV metric meaning,
budgets, retries, cancellation, cooldowns and genuine error precedence.

## Compatibility and verification

Leave policy-only automatic/select actions, failed/skipped reevaluation,
initial/non-adopted/generic/legacy paths and current fulfilled verification
assembly unchanged. Preserve scoring, mode/capability checks, deterministic
adoption, comparison/rollout and routing/learning authorization.

Verify genuine native/compatibility proof versus copied/offline/mutated/overflow
sources, exact item/pool/stage/candidate binding, outer context shape, label
independence and no old nested support. Keep original baseline and candidate
identity, maximum outcome confidence, restrictive authority, explicit top-level
signals/RAG and error/counter behavior. Exercise cap/resilience/mode skips,
genuine failures, all four fulfilled outcomes and existing forced-gap precedence.

Use real evaluator/owner and loopback HTTP controls, plus isolated production-
factory PostgreSQL persistence/load, advisory/signals/RAG projections, BIGINT
binding, concurrency/rollback/lost acknowledgement, stale fingerprint refusal,
both Discord paths and exact completed replay. Deliberately exercise later
mutation without claiming terminal/writer context revalidation. Existing frame
checks must still suppress unavailable review evidence.

Run fresh affected backend coverage, focused browser/contract checks and normal
quality/security gates. Reuse client evidence only after unchanged inputs,
installed graph and report hashes are verified. Keep design and observed outcome
separate, update Unreleased, maintain local artifacts, commit/push all intended
changes on main and inspect the exact-source CI.

No new schema, public field, query, provider request, API/UI, setting, scheduled
job, operator CLI trigger, historical inference, live configuration write,
release or deployment is included. There are no open PRs at intake; recheck at
delivery and perform applicable dependency work only if a genuinely eligible
open PR exists, within a separately assessed scope.

## Trade-offs and recommendation stack

Fresh minimal context preserves useful policy mechanics while explicit null
avoids inheriting unrelated support. The costs are new advisory fingerprints,
possible removal of nested persistence fallbacks, and a deliberately limited
construction-time guarantee. Continuing validation could catch later loss, but
would add distinct ownership/copy/writer rules and is deferred.

Recommended stack: independent live numeric source, exact construction binding,
minimal policy context or null, advisory absence until a current fulfilled
outcome, existing final apply and saved-frame validation, ordinary transactional
persistence, then completed-answer replay. Keep policy provenance, AI output and
authorization separate. All behavior decisions were confirmed before runtime
implementation.
